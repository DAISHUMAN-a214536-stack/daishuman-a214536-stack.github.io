LAB OVERVIEW · SCENARIO & PROBLEM STATEMENT Context Verified

Secure User Management Overview

Project Scenario: Many mobile applications face security risks because they do not protect local user data or check user access properly. This project presents an Android app that implements key security controls, such as PBKDF2 password hashing, role-based access, and account lockout. It demonstrates how to apply secure programming principles to build a safe user management system.

Problem Statement: Standard Android user management apps often lack strong access controls, store credentials insecurely, and expose detailed login errors. These security gaps leave user accounts vulnerable to unauthorized access, credential leaks, and brute-force attacks.

CASE 01 · INPUT VALIDATION Implemented · Verified

Input Validation and Login Protection

Baseline: Registration initially saved the username and password without input checks.

⚡ Before code (illustrative baseline) ▾ 
fun register(username: String, password: String) {
    // No input checks
    saveUser(username, password)
}

Code change: SecurityUtils.kt: validateRegistration() validates the username, password length, and password confirmation. Login failure handling is in UserRepository.kt, login().

🔒 Current project code (source excerpts) ▾ 
// SecurityUtils.kt: validateRegistration()
if (normalizedUsername.isBlank()) return "Username is required."
if (normalizedUsername.length !in 3..32) {
    return "Username must be 3 to 32 characters long."
}
if (password.length < MIN_PASSWORD_LENGTH) {
    return "Password must be at least 12 characters."
}
if (confirmPassword != password) return "Passwords do not match."

Principles: Input Validation · Authentication · Account Security

Reflection: Validating input before saving an account prevents invalid registration data from entering the system. Login error handling also gives users feedback when authentication fails.

CASE 02 · PASSWORD SECURITY Implemented · Verified

Password Hashing and Password Change

Baseline: The illustrative baseline stores a password as plain text and compares the entered password directly with the stored value. This is not verified as the original project code.

⚡ Before code (illustrative baseline) ▾ 
data class User(
    val username: String,
    val password: String // Stored in plain text
)
fun login(input: String, user: User) = input == user.password

Code change: SecurityUtils.kt: PasswordHasher uses PBKDF2WithHmacSHA256 with 120,000 iterations. UserRepository.kt: changePassword() verifies the current password, generates a new salt, hashes the new password, and updates the user record.

🔒 Current project code (source excerpts) ▾ 
// SecurityUtils.kt: PasswordHasher
private const val ITERATIONS = 120_000
val factory = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256")
 
// UserRepository.kt: changePassword()
if (!PasswordHasher.verify(currentPassword, user.salt, user.passwordHash)) {
    return@withContext Result.failure(
        IllegalArgumentException("Current password is incorrect.")
    )
}
val newSalt = PasswordHasher.generateSalt()
val newHash = PasswordHasher.hash(newPassword, newSalt)
userDao.update(user.copy(passwordHash = newHash, salt = newSalt))

Principles: Password Hashing · Authentication · Data Protection

Reflection: Password hashing reduces the risk of exposing original passwords if stored data is accessed. Verifying the current password and generating a fresh salt also help protect the password-change process.

CASE 03 · SESSION SECURITY Implemented · Verified

Encrypted Session Storage

Baseline: The illustrative baseline stores the user ID and role in ordinary SharedPreferences. This is not verified as the original project code.

⚡ Before code (illustrative baseline) ▾ 
val prefs = context.getSharedPreferences("session", Context.MODE_PRIVATE)
prefs.edit().putLong("user_id", userId).putString("role", role).apply()

Code change: SecurityUtils.kt: SessionManager uses EncryptedSharedPreferences with an AES-256-GCM MasterKey, AES256_SIV for preference keys, and AES256_GCM for preference values.

🔒 Current project code (source excerpts) ▾ 
// SecurityUtils.kt: SessionManager
private val encryptedPrefs = EncryptedSharedPreferences.create(
    context,
    "secure_user_management_session",
    MasterKey.Builder(context).setKeyScheme(MasterKey.KeyScheme.AES256_GCM).build(),
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)
 
fun saveSession(userId: Long, username: String, role: String) {
    encryptedPrefs.edit().putLong("user_id", userId)
      .putString("username", username).putString("role", role).apply()
}

Principles: Data Confidentiality · Secure Session Management

Reflection: Encrypting session data helps protect locally stored identity and role information. Session handling should still be tested to ensure logout clears or invalidates the active session as intended.

CASE 04 · DATABASE & AUDIT LOGGING Implemented · Verified

Room Database and Activity Logs

Baseline: The illustrative baseline stores users in an in-memory list and has no persistent storage or activity log. This is not verified as the original project code.

⚡ Before code (illustrative baseline) ▾ 
val users = mutableListOf<User>()
fun addUser(user: User) {
    users.add(user) // Memory only
}
// No persistent storage or activity log

Code change: UserData.kt: UserDao provides database queries and update operations. UserRepository.kt: logAction() inserts an ActivityLogEntity with the user ID, username, action, and timestamp.

🔒 Current project code (source excerpts) ▾ 
// UserData.kt: UserDao
@Query("SELECT * FROM users WHERE username = :username LIMIT 1")
suspend fun getByUsername(username: String): UserEntity?
 
@Update
suspend fun update(user: UserEntity)
 
// UserRepository.kt: logAction()
activityLogDao.insert(
    ActivityLogEntity(
        userId = userId,
        username = username,
        action = action,
        timestamp = System.currentTimeMillis()
    )
)

Principles: Data Persistence · Accountability · Audit Logging

Reflection: A Room database supports persistent user records, while activity logs help trace important actions. Logs are most useful when they accurately identify the actor and record meaningful security-related events.

Secure User Management

Scenario & Problem Statement: Modern Android mobile applications handle critical personal identities and credentials, making them prime targets for unauthorized access, data exfiltration, and injection attacks. Secure User Management demonstrates a defense-in-depth architecture addressing authentication weaknesses, insecure direct object references, and data exposure in local storage. By implementing Role-Based Access Control, cryptographic credential protection, parameterized database queries, and brute-force account lockout, the project provides a hardened and verifiable user lifecycle solution.

Reflection

Team learning reflection

Team Reflection & Learning Journey

Developing the Secure User Management e-Portfolio provided our team with deep insights into defensive application architecture and threat modeling. We discovered that implementing robust security controls—such as PBKDF2 credential hashing, strict RBAC authorization boundaries, and parameterized Room queries—is essential for mitigating common mobile vulnerabilities. Collaborative code reviews, continuous emulator testing, and live video validations helped us verify each defense mechanism objectively. This hands-on journey strengthened our collective engineering rigor and taught us to design resilient software from the ground up.

Most Important Principle

Authorization and Data Integrity are paramount. Enforcing role checks directly at the Room repository boundary ensures that privileged administrative functions cannot be bypassed simply by manipulating UI visibility.

Greatest Vulnerability

Insecure credential exposure and unthrottled authentication. Exposing password hashes in admin queries or permitting unlimited failed login attempts leaves systems vulnerable to offline attacks and brute-force credential stuffing.

Three Key Improvements

1. Multi-factor authentication (MFA) for administrative accounts; 2. Centralized tamper-evident audit log streaming with cryptographic signatures; 3. Native biometric authentication integration via Android BiometricPrompt.
